UOM Forge 架构实现分析

回答「代码是怎么组织的、为什么这么组织、数据怎么流」。五层结构、八级校验管道、一次建模的十环链路，全部以文件与行号为证。

分析对象 F:/caochun/uom-forge核心代码 约 1,615 行验证 npm test 3/3 通过日期 2026-09-10
结论先行：UOM Forge 是「LLM 生成、服务端守护、人类确认」的三方协作系统。架构分五层且依赖方向严格单向；全系统脊柱是一条八级校验管道，最有辨识度的设计是逐字引文闸门 —— 宁可没有证据，不可伪造证据。

1仓库总览与职责分配

UOM Forge 是「LLM 生成 · 服务端守护 · 人类确认」的三方协作系统。浏览器只负责证据呈现与结果审阅，所有 LLM 交互、JSON 解析、模型规范化与证据校验都在 Vite 服务端中间件与 server/ 守护层完成。

契约层用 51 行完成三件事：定义候选模型形态、规定每个元素必须携带证据、提供前后端共用的派生函数。

shared/model-contract.js:3-5, 34-38
const record = (properties) => ({ type: 'object', additionalProperties: false, properties,
                                  required: Object.keys(properties) })
export const evidence = list(record({ blockId: text, quote: text }))   // 全系统最小信任单元

export function activityCoverage(activity) {          // 覆盖率不存数字，由 requirement 推导
  const requirements = activity.requirements || []
  if (!requirements.length) return null
  return Math.round(requirements.filter((item) => item.status === 'covered').length / requirements.length * 100)
}
设计选择结构性后果
actions 与 functions 拆成两个集合，而非一个 sideEffect 布尔字段「改变状态的操作」与「只读能力」在 schema 层就是不同类型，校验器与 UI 都能结构性区分（提示词第 9 条同步强调 functions 不能有副作用）
每个集合的 record() 都设 additionalProperties: false 且 required 为全部键Provider 少给一个字段、多给一个字段都会被抓出来，不存在「宽松通过」
evidence 出现在每个元素与每个 requirement 上证据不是可选注释，而是元素能否存在的必要条件
activityCoverage / modelDiff 放在 shared 而非某一层前后端使用同一实现，覆盖率数字不会两边漂移

3服务端守护层：八级校验管道

五个阶段入口在 codex-acp.js 中共享同一条管道——这是全系统可信性的核心结构：

server/codex-acp.js:12-17
export async function analyzeWithProvider(document, currentModel, instruction = '', options = {}) {
  validateDocument(document)                                                    // ① 文档闸门
  const text = await runProviderTurn(modelingPrompt(document, currentModel, instruction), options)  // ② 注入防御
  const model = hydrateEvidence(normalizeModel(parseModel(text)), document)      // ③④⑤ 解析/归一/修剪/修复
  const validation = validateModel(model, document)                             // ⑥⑦⑧ schema/引用/逐字引文
  return { model, validation }
}

8架构评估

优势

1 · 可信写入链完整且可解释

八级闸门 + 每条错误都指明具体元素（「关系 X 的端点不是已有对象」「引文不在原文证据块 Y 中」）。3 个单测直接固化关键行为：紧凑词汇归一、伪造引文拒绝、转述引文丢弃。

2 · 依赖方向纯净，复用真实发生

契约层零依赖被前后端共用；换 Provider 只需加一个 runXxxTurn，分发点只有 4 行。

3 · 阶段隔离防交叉污染

narrate 物理上不传 document，使「模型自述」成为对模型完备性的独立探针。

4 · 失败路径全显式

超时、进程退出、非 end_turn、HTTP 非 200、JSON 解析失败均有具名错误；UI 保留上一轮草稿；演示数据在源码层已被删除而非「不启用」。

代价

1 · 校验全有全无

validateModel 抛错即整轮作废（analyzeWithProvider 不捕获、不重试、不局部接受）。一条引文被改写 → 数十秒推理与其余正确元素一起丢弃。缺少「局部拒绝 + 定点重生成」的中间态。

2 · 单文件前端 + 单进程服务端

649 行 main.jsx 承载五视图 + SSE + 状态管理，无路由无拆分；systemd 的 ExecStart 实质运行的是 npm run dev。

3 · 宽容归一侵蚀 id 稳定性

slug(name) 补 id 使命名漂移时 modelDiff 把「改名」统计成一删一增；有 schemaVersion 但无迁移工具。

4 · 空白归一的双标

normalized 抹掉全部空白后比对：中文安全，英文场景下「仅空白被重排」的引文可逃过检测。
